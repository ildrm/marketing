# Channel capability and activation matrix

Research checked **2026-09-27** against official vendor documentation. This file describes possible official routes, not activated integrations. Provider terms, regional availability, and prices need fresh review before activation. The current code has a generic in-memory sandbox adapter contract for SMS, WhatsApp, email, RCS, and push. SMS alone is wired to a persistent sandbox permission record and message log; it is not connected to campaign sending or a live provider.

| Channel / format | Delivery and verification route | Metric provenance / identity boundary | Current status | Activation prerequisites |
|---|---|---|---|---|
| Newsletter sponsored section | Owner publishes; operator/manual proof review | Owner-reported publication, platform-observed link click, advertiser-imported conversion. No subscriber list sharing. | **Runnable manual sandbox** | Owner agreement, verified audience evidence, proof standard, cancellation and make-good terms. |
| Website native/display slot | Publisher tag; site ownership via DNS/file/tag | Platform-observed request/serve/click; viewability needs explicit SDK definition. Anonymous until consented first-party action. | **Unimplemented** | Tag, placement security, pacing, fraud controls, ads.txt/sellers.json review. |
| Telegram channel/bot/Mini App | Authorized bot/admin functions where the bot has access; otherwise manual post booking. [Telegram Bot API](https://core.telegram.org/bots/api) documents `channel_post`, `getChatMember`, and bot-mediated interactions. | Bot-observed updates where authorized; public views do not identify people. | **Research only** | Bot token, admin rights, property verification, webhook validation, channel permissions, regional policy review. |
| WhatsApp Channel/Status sponsorship | Owner-managed manual placement unless an official matching API is verified. | Owner-reported proof and platform link click; no subscriber export. | **Research only** | Owner contract, official access confirmation, proof review. |
| Creator/social/offline QR/app placement | Owner deliverable and manual/authorized proof | Owner-reported proof, platform-observed QR/link click. | **Unimplemented** | Contract, proof, asset and fraud policy, channel-specific access. |

| WhatsApp Business to advertiser-owned contacts | Meta's [official Cloud API documentation and collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) and [sample code](https://github.com/fbsamples/whatsapp-api-examples) cover templates, sends, and webhook signature examples. | Provider-reported message states where supported; opted-in contact and approved template required. | **Contract-tested in-memory sandbox only** | Business/WABA and phone verification, templates, opt-in evidence, access token, signed webhook, pricing and country review. |

| Push | Browser/app permission and service worker route | Subscription/permission status and provider feedback; human read is not implied. | **In-memory sandbox primitive** | Permission UX, withdrawal, subscriptions, key rotation, app/site implementation. |

## Adapter contract currently implemented

`packages/integrations/messaging.mjs` exposes `capabilities()`, `estimate()`, `send(message, permission)`, and `simulateStatus()` for deterministic sandbox behavior. SMS has E.164 formatting validation, GSM-7/UCS-2 segment preflight, an explicit configurable segment price, and timezone-aware quiet-hours helper. The API persists tenant-scoped, purpose-specific SMS permission evidence, a one-way keyed contact digest, withdrawal, message acceptance, idempotency and an operator-only status simulation. It stores a content hash, not SMS body or raw number. This remains a **sandbox**: no network send, global suppression, real queue, provider routing, signed webhook, cost reconciliation, or opt-out race handling. Test coverage is in `tests/messaging.test.mjs` and `tests/journey.test.mjs`.

## Framework/runtime verification

Local Node was v26.5.0. The [Node release page](https://nodejs.org/en/about/previous-releases) listed v26 as Current and v24 as LTS on 2026-09-27. `node:sqlite` documentation describes synchronous `DatabaseSync`; it was a release candidate in [Node 26 documentation](https://nodejs.org/api/documentation.html). [Next.js security updates](https://nextjs.org/blog) showed 16.3.6 as the active LTS release as of this review, with a further scheduled security release. [NestJS migration documentation](https://docs.nestjs.com/migration-guide) discusses v11 to v12. No Next/Nest package versions are pinned because those frameworks are **not implemented** in this sandbox. The Docker demo pins Node 26.10.0, documented in the [Node release post](https://nodejs.org/en/blog/release/v26.10.0). A production stack must choose LTS versions and run a new compatibility/security review.
